# Developing hinote

The repository is a Bun workspace. Each package lives in `packages/`:

- `packages/hinote`: the `hinote` package, the CLI and the core components.
- `packages/chart`: `@hinote/chart`, `<Chart>`, TanStack Charts drawn on the server. The page gets each step's scene as JSON and animates between them with `src/client.ts`, which `<Chart>` adds for the CLI to bundle; `src/scene.ts` rebuilds the scales' `map` functions JSON drops. Like the other packages it does not import hinote: it writes the markup `<Script>` and `<Steps>` write, as `@hinote/types` describes it, and types `window.hinote` from there.
- `packages/code`: `@hinote/code`, the `<Code>` component. It depends on `@pierre/highlights` so that `hinote` does not.
- `packages/d2`: `@hinote/d2`, `<D2>`, D2 diagrams drawn as SVG with `@terrastruct/d2`. The compiler is WebAssembly in a worker thread; the component draws one diagram at a time and holds the worker only while it draws, so a build exits when it is done.
- `packages/katex`: `@hinote/katex`, `<Math>`, LaTeX as MathML with KaTeX.
- `packages/mermaid`: `@hinote/mermaid`, `<Mermaid>`, Mermaid diagrams drawn as SVG with `beautiful-mermaid`, which needs no DOM. Its colors are the deck's CSS variables, and the component scopes the renderer's `<style>` and ids to each diagram, since every slide is on one page.
- `packages/types`: `@hinote/types`, the types shared by `hinote` and the `@hinote/*` packages, such as `Theme` and `SlideContext`. It is one hand-written `index.d.ts` with no JavaScript. `hinote` re-exports what it holds.

How to use a package is its guide, `packages/hinote/skills/<name>/SKILL.md`, named after the package (`chart` for `@hinote/chart`). The guides ship with hinote, so `hinote skills get chart` works before the package is installed, and the core guide lists them. A package's README says only what the package is and where its guide is. Change the guide in the same commit as the package. Two guides belong to no package: `core`, for hinote itself, and `talk`, for planning a talk and its slides.

Run `bun install` once at the root. The root `package.json` is private and holds the workspace and the dev dependencies every package uses: TypeScript, `@types/bun`, `hono`, and the linters. A package lists only what it needs beyond those. hinote has `hono` as a peer, so a deck brings the one Hono it serves with; the component packages list what they use, `hono` included, as plain dependencies. A range more than one package names, such as `hono`'s, is written once in the root's `workspaces.catalog`, and the packages write `catalog:`; a package of this workspace is named as `workspace:^`. `tsconfig.base.json` holds the compiler options every package extends, and its `paths` point `hinote` and `@hinote/types` at their source, so the `@hinote/*` packages' tests render through `hinote` without depending on it. `.oxlintrc.json` holds the lint rules.

To try a change against a real deck, run `bun src/cli.ts init .tmp/talk --no-install` and then `bun src/cli.ts dev .tmp/talk` in `packages/hinote`.

`packages/hinote/src/client/main.ts` runs in the browser, and every page inlines it. From source, `src/client/script.ts` bundles it with `Bun.build` when hinote loads, so tests and `hinote dev` always run the current client. `bun run build` writes the bundled text into `dist/`, so the published package never needs a bundler.

`bun run build` builds every package; in one package it builds that one. Each package's `dist/` is its `src/` compiled file for file by tsdown, on Rolldown, with declarations from TypeScript, by `scripts/build-package.ts` and the package's `tsconfig.build.json`. Nothing is bundled, and each package declares `"sideEffects": false`, so a deck's bundler keeps only the modules the deck imports. `prepack` builds before packing. A package ships `dist/` and not `src/`, so Bun and Node load the same JavaScript. hinote's `scripts/build-lib.ts` adds the CSS module declaration, which is not compiled, and the bundled browser runtime. `bun test` in hinote also builds `dist/` and runs it under Node when Node is installed.

Before committing, run `bun run test`, `bun run typecheck`, and `bun run lint` at the root; each runs the same script in every package. `lint` runs [oxlint](https://oxc.rs/docs/guide/usage/linter) with the rules in `.oxlintrc.json` (each rule turned off there says why), including the type-aware ones that `tsrs` runs, and then each package's `lint`. In `packages/hinote` that is [oxdg](https://www.npmjs.com/package/oxdg), which fails on a circular import between modules in `src/`. `createSlide` lives in `src/deck/create.ts` for that reason: it builds decks, and a deck renders slides.

## Releasing

All packages share one version and are released together. Every change that reaches users, in any package, adds a line under `## Unreleased` in `packages/hinote/CHANGELOG.md`. To release, rename that heading to the new version, run `bun scripts/version.ts <version>` to set it in every package, and merge to `main`. CI runs `bun scripts/version.ts`, which fails when the versions differ. Then publish a GitHub release tagged `v<version>` whose body is that version's section of the changelog, not only a compare link. Publishing the release runs `.github/workflows/publish.yml`, which checks that the tag matches the packages' version, then packs each package with `bun pm pack` and publishes the tarball with `npm publish`, `@hinote/types` first. Packing turns `catalog:` and `workspace:` ranges into plain versions; `npm publish` on its own would leave them as they are.
